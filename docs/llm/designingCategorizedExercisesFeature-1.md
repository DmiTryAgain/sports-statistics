# Проектирование категоризированных упражнений с дополнительными параметрами

## Контекст

Текущая реализация поддерживает только упражнения с количеством повторений (reps). Нужно расширить бота для поддержки упражнений с дополнительными параметрами: масса (жим лёжа, становая тяга), дистанция + время (бег, велосипед), только время (планка). При этом необходимо сохранить обратную совместимость с текущей текстовой логикой.

---

## Классификация упражнений по параметрам

| Тип | Параметры | Примеры |
|-----|-----------|---------|
| **Reps** (текущий) | кол-во | подтягивания, отжимания, пресс |
| **Reps + Weight** | кол-во + масса | жим лёжа, становая тяга, присед со штангой |
| **Distance + Duration** | дистанция + время | бег, велосипед, плавание |
| **Duration only** | время | планка, вис на турнике |
| **Reps (machine)** | кол-во + масса | тренажёры (по сути то же, что Reps+Weight) |

---

## Рассмотренные идеи

### Идея 1: Текст с суффиксами единиц измерения

Пользователь пишет числа с приклеенной единицей:

```
сделал жим 80кг 10
пробежал 5км 25мин
сделал планку 90сек
сделал присед 60кг 12
```

**Как это работает:** после распознавания упражнения бот знает его тип и ожидаемые параметры. Оставшиеся слова парсятся по регулярке `(\d+[\.,]?\d*)(кг|kg|км|km|м|m|мин|min|сек|sec|ч|h)` — число + суффикс. Голое число без суффикса интерпретируется как количество повторений (обратная совместимость).

**Достоинства:**
- Полная обратная совместимость — текущие упражнения работают как раньше
- Один шаг, быстрый ввод для опытных пользователей
- Не нужна новая инфраструктура (кнопки, состояния)
- Естественно звучит: "пожал 80кг 10" — так люди и говорят

**Недостатки:**
- Нужно помнить формат и суффиксы (хотя они интуитивны)
- Парсинг становится сложнее: нужно отличать "5км" от "5" в разных контекстах
- Если пользователь забудет суффикс при вводе веса ("жим 80 10") — непонятно, что 80, а что 10
- Единицы измерения на двух языках удваивают словарь суффиксов

---

### Идея 2: Пошаговый диалог (мультишаговый ввод)

После команды бот задаёт вопросы по очереди:

```
User: сделал жим
Bot:  Какой вес? (кг)
User: 80
Bot:  Сколько повторений?
User: 10
Bot:  Добавлено
```

**Достоинства:**
- Максимально user-friendly — не нужно ничего запоминать
- Невозможно перепутать параметры
- Бот сам подсказывает единицы измерения
- Легко расширять на новые параметры

**Недостатки:**
- Медленно: 3-4 сообщения вместо одного
- Нужно хранить состояние диалога (сессия пользователя) — сейчас бот stateless
- В групповом чате выглядит шумно
- Ломает текущую модель "одно сообщение = одно действие"
- Сложнее реализовать: таймауты, отмена, конкурентные диалоги

---

### Идея 3: Inline-кнопки (Inline Keyboard)

После команды бот предлагает кнопки:

```
User: сделал жим
Bot:  Жим лёжа — введи параметры:
      [60кг] [70кг] [80кг] [90кг] [Другой вес]
User: *нажимает 80кг*
Bot:  Повторений:
      [5] [8] [10] [12] [Другое]
User: *нажимает 10*
Bot:  Добавлено. Жим лёжа: 80кг x 10
```

**Достоинства:**
- Очень удобно: минимум набора текста
- Можно предлагать "любимые" значения на основе истории пользователя
- Визуально понятно, что от тебя хотят
- Кнопки обновляются in-place (не засоряют чат)

**Недостатки:**
- Сложная реализация: callback queries, состояние, обновление сообщений
- Ограничение Telegram: максимум 8 кнопок в ряду, суммарно до 100
- Не подходит для произвольных значений (нестандартный вес/дистанция)
- Нужна fallback-логика для нестандартных значений
- Требует серьёзного рефакторинга — текущая архитектура не рассчитана на stateful-диалоги

---

### Идея 4: Гибрид — текст с суффиксами + подсказки кнопками

Комбинация идей 1 и 3:

```
# Путь A — опытный пользователь, всё одним сообщением:
User: сделал жим 80кг 10
Bot:  Добавлено. Жим лёжа: 80кг x 10

# Путь B — новый пользователь, не указал параметры:
User: сделал жим
Bot:  Жим лёжа — нужно указать вес и повторения.
      Можешь написать: "80кг 10"
      Или выбери вес:
      [60кг] [70кг] [80кг] [90кг] [Ввести вручную]
```

Бот сначала пытается распарсить всё из одного сообщения. Если параметров не хватает — предлагает кнопки или просит дописать.

**Достоинства:**
- Обратная совместимость сохраняется полностью
- Быстрый ввод для опытных, подсказки для новичков
- Гибкость: кнопки помогают, но не навязываются
- Постепенная миграция: можно начать только с текста, добавить кнопки позже

**Недостатки:**
- Самая сложная реализация из всех: два пути ввода
- Всё равно нужно хранить состояние для пути B (хотя бы минимально)
- Нужно продумать UX перехода между путями

## Рекомендация: поэтапная реализация

### Этап 1 — Текст с суффиксами (минимальные изменения)

Даёт результат быстро, сохраняет архитектуру и обратную совместимость.

**1. Категории упражнений** — тип упражнения определяет, какие параметры ожидаются:

```go
type ExerciseCategory int

const (
    CategoryReps         ExerciseCategory = iota // подтягивания: count
    CategoryRepsWeight                           // жим: count + weight
    CategoryDistTime                             // бег: distance + duration
    CategoryDuration                             // планка: duration
)
```

**2. Парсинг значений с суффиксами** — после распознавания упражнения остаток разбивается на пары `число+суффикс`:

```
"80кг 10" -> weight=80kg, count=10
"5км 25мин" -> distance=5km, duration=25min
"90сек" -> duration=90sec
```

Словарь суффиксов:
```
кг/kg -> weight (kg)     |  мин/min -> duration (min)
км/km -> distance (km)   |  сек/sec/с/s -> duration (sec)
м/m  -> distance (m)     |  ч/h -> duration (hour)
```

Голое число (без суффикса) = count (повторения). Это обеспечивает 100% совместимость с текущим вводом.

**3. Валидация по категории** — бот знает, что `жим` это `CategoryRepsWeight`, значит ожидает weight + count. Если чего-то не хватает, сообщает:

```
User: сделал жим 80кг
Bot:  Для жима нужно указать количество повторений. Например: "жим 80кг 10"
```

**4. Хранение в params (jsonb):**

Нормализованный вариант (рекомендуется — проще агрегировать):

```json
{"weightKg": 80}
{"distanceM": 5000, "durationSec": 1500}
```

Нормализация позволяет на входе принимать любые единицы (`5км`, `5000м`), а хранить всегда в базовых (метры, секунды, кг). На выходе — конвертировать обратно в удобный формат.

**5. Вывод статистики** — группировка всегда по всем доп. параметрам.

Это сохраняет реальную картину тренировки: видно, сколько подходов и повторений было на каждом весе/дистанции. Агрегация вроде "макс вес + общее кол-во" теряла бы эту информацию.

```
# Reps (текущий формат, без изменений):
упражнение      кол-во    подходы
подтягивания    45        3

# Reps + Weight (GROUP BY exercise, weightKg):
# Пример: 5 подходов жима — 20кг x10, 50кг x10, 70кг x10, 70кг x10, 70кг x10
упражнение    вес     кол-во    подходы
жим лёжа      20кг    10        1
жим лёжа      50кг    10        1
жим лёжа      70кг    30        3

# Distance + Duration (GROUP BY exercise, distanceM):
# Пример: 3 пробежки — 5км за 25мин, 5км за 27мин, 10км за 55мин
упражнение    дистанция    время         подходы
бег           5км          52мин         2
бег           10км         55мин         1

# Duration only (GROUP BY exercise):
упражнение    время       подходы
планка        4мин 30сек  3
```

### Этап 2 (в будущем) — Кнопки как дополнение

Когда текстовый ввод уже работает, можно добавить inline-кнопки как **альтернативный путь** для случаев, когда пользователь не указал обязательные параметры.

## Единицы измерения: вход, хранение, выход

Ключевое решение: **на входе — гибкость, внутри — нормализация, на выходе — smart-форматирование**.

```
Ввод: "пробежал 5км 25мин"
           |
Парсинг: distance=5km -> 5000m, duration=25min -> 1500sec
           |
БД: {"distanceM": 5000, "durationSec": 1500}
           |
Вывод: 5км, 25мин  (автоматически выбирается удобная единица)
```

Правила автоформатирования на выходе:
- distance < 1000м -> показывать в метрах, иначе в км
- duration < 60сек -> секунды, < 60мин -> мин:сек, иначе ч:мин
